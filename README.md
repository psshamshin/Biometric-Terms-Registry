# Реестр терминов и метрик по биометрии из ГОСТов

## 1. Что делает инструмент

Инструмент читает PDF терминологических ГОСТов по биометрии и собирает из них реестр терминов и метрик (FMR, FNMR, FAR и т. п.).
На выходе — реестр каждого стандарта и общий реестр, в котором одна метрика занимает одну строку, а формулировка каждого стандарта стоит в своей колонке.
Формулировки берутся из стандартов дословно; ошибки распознавания исправляются только по таблице с основанием по скану.
Парсер не пишет тексты для людей (длинное и короткое определение, формулу) — их добавляет генерация текстов через `data/curated/`.
Колонки «Есть в NIST» и «Забираем в MRR» заполняет потребитель реестра. Внешних сервисов инструмент не использует.

## 2. Как устроен конвейер

1. **Извлечение** — текст каждой страницы PDF.
2. **Очистка** — убираются колонтитулы, номера страниц и служебные строки, склеиваются переносы; каждое изменение пишется в журнал.
3. **Разбиение** — текст раздела «Термины и определения» режется на статьи по номеру пункта.
4. **Разбор** — из статьи берутся наименования, аббревиатуры, синонимы, определение, примеры и примечания.
5. **Тип и статус** — метрика или термин по двум признакам из схемы; метрика получает «черновик», термин — «отложено».
6. **Область** — по разделу стандарта и исключениям по пунктам из конфига стандарта.
7. **Ключ и id** — ключ для объединения и короткий идентификатор записи.
8. **Пары** — парная метрика по правилам из схемы (non-, accept/reject, negative/positive).
9. **Реестр стандарта** — `data/out/<std_id>/` и отчёт по стандарту.
10. **Объединение** — записи всех стандартов с одинаковым ключом сливаются в одну строку общего реестра.
11. **Слой curated** — в общий реестр подмешиваются тексты и статусы из `data/curated/`.
12. **Проверки** — схема, справочники, нумерация, целостность, эталоны, регрессия.
13. **Отчёты** — `report.md` по стандарту, `merge_report.md` по объединению; разделы 3, 6 и 9 этого README.

## 4. Как запустить

Нужен Python 3.12.

```bash
python3.12 -m venv .venv
.venv/bin/pip install -r requirements.txt

.venv/bin/python run.py                            # все стандарты, объединение, разделы README
.venv/bin/python run.py config/<std_id>.yaml       # один стандарт → data/out/<std_id>/
.venv/bin/python -m pytest -q                      # все проверки
```

Повторный запуск даёт побайтно те же файлы.

## 5. Как подключить новый стандарт

1. Положить PDF в `data/raw/`.
2. Выполнить `prompts/add_gost.md` — через GitHub это issue «Добавить ГОСТ» (раздел «Работа через GitHub»).
3. Ответить на вопросы разведки: колонка, url, области, приоритет, исправления распознавания.
4. В отчёте стандарта проверить: нарушений схемы 0, эталон без расхождений, флаги объяснены; в `merge_report.md` — конфликты объединения.

## 7. Ключ и id

- **Ключ** — по нему объединяются записи разных стандартов: «Аббревиатура en | Область», а если аббревиатуры нет — «Наименование en | Область». Пример: `FNMR | биометрия · верификация`.
- **id** — короткий постоянный идентификатор строки для ссылок и для файлов `data/curated/<id>.yaml`: аббревиатура en строчными или slug наименования en. Пример: `fnmr`, `biometric-template`.

Одна метрика в двух стандартах имеет один ключ и одну строку общего реестра; id берётся из первого по `priority` стандарта.

## 8. Статусы и типы

**Типы сущности:**
- **метрика** — выполнены оба признака из схемы: аббревиатура вида «…R» (или наименование на «rate») и определение со слов «Доля», «Вероятность», «Частота», «Коэффициент»;
- **термин** — всё остальное; если выполнен один признак — флаг `type_conflict`;
- **понятие** — есть в справочнике, парсер его не ставит.

**Статусы:**
- **черновик** — метрика от парсера, ждёт текстов и проверки человеком;
- **отложено** — термин; в работу пока не берётся;
- **утвержден** — ставит только человек, через `data/curated/`; требует заполненных текстов и формулы;
- **устарел** — есть в справочнике, ставит только человек.

## 10. Проверки

- **Схема** — каждое значение проходит ограничение своей колонки из `config/registry_schema.yaml`.
- **Справочники** — тип, статус и область только из справочников; «утвержден» и «устарел» — только из `data/curated/`.
- **Нумерация** — в каждом разделе стандарта нет пропусков и повторов номеров.
- **Целостность статьи** — в определении нет чужого номера, колонтитула, обрыва на «-», «,», «:».
- **Полнота по указателю** — если в стандарте есть алфавитный указатель, каждый его термин найден в статьях и наоборот.
- **Дубли ключа** — информация: такие записи сливаются при объединении.
- **Связи** — каждая парная метрика есть в реестре; метрики без пары перечислены.
- **Эталоны** — 3–6 статей каждого стандарта, переписанных по изображениям страниц, совпадают с разбором посимвольно.
- **Регрессия** — выход каждого стандарта побайтно совпадает с его базовой копией; `registry.sqlite` сверяется по строкам с `registry.json`.
- **Повторный запуск** — два прогона дают побайтно одинаковые файлы.
- **README** — разделы 3, 6 и 9 совпадают с конфигами и схемой.

## 11. Отчёты

- **`data/out/<std_id>/report.md`** — воронка, флаги, нарушения схемы, указатель, эталон, журнал очистки, таблица метрик.
- **`data/out/merge_report.md`** — записи по стандартам, объединённые строки, конфликты, проверки общего реестра, слой curated, метрики.
- **`data/out/<std_id>/abbreviations.csv`** — раздел «Сокращения» стандарта, если он есть.
- **Журнал очистки** `data/interim/<std_id>/cleaning_log.csv` — каждое изменение текста: страница, было, стало, правило. Создаётся при прогоне, в репозиторий не входит.

## 13. Принятые решения

- Колонки источников — только у подключённых стандартов, в порядке `merge.yaml`.
- Формулировки — дословно; исправления распознавания — только по таблице в конфиге стандарта с основанием по скану.
- «исключен» в заголовке — устаревший термин, статья остаётся; он идёт в «Исключённые», не в синонимы.
- Синонимы: варианты через «/», пометка «(синоним)», краткие формы после «; »; русские и английские варианты сопоставляются по порядку.
- Обозначения с параметрами («ВЛОИ (N, R, T)») — не синонимы, а первая строка «Примечаний»; основа становится аббревиатурой, если обычной нет.
- Уточнение области в скобках после английского термина — первая строка «Примечаний».
- Примечания нумеруются по порядку появления, а не по распознанной цифре.
- Мягкий перенос в конце строки склеивается без дефиса; дефис в конце строки — по тексту стандарта, иначе латиница сохраняет дефис, кириллица склеивается (`hyphen_guess`).
- Повторы внутри стандарта и пересечения стандартов сливаются только на объединении; одинаковый ключ — одна строка.
- Пары метрик: приставка non-, пары accept/reject и negative/positive.
- Признаки метрики не расширяются без согласования (SEL, pre-selection error, penetration rate — термины).
- Метрика без пары — «—» и `no_pair`; метрика без формулы — `formula_na`, формула к «утвержден» не требуется.
- «утвержден» ставит только человек через `data/curated/`.
- `registry.sqlite` не хранится в репозитории: его байты зависят от версии SQLite; содержимое сверяется с `registry.json`.
- После подключения стандарта заводится его базовая копия; регрессия проверяет все стандарты.
- Сверка с Miro не выполняется: инструмент с Miro не связан (у 2382-37 сверка осталась из первой версии).

## Работа через GitHub

Всё делается в браузере на github.com, ничего не нужно запускать у себя.

**1. Загрузить PDF.** Откройте репозиторий → папка `data/raw` → кнопка **Add file → Upload files** → перетащите PDF → внизу **Commit changes**.

**2. Открыть задачу.** Вкладка **Issues → New issue** → выберите шаблон:
- «Добавить ГОСТ» — замените в тексте `ИМЯ_ФАЙЛА` на имя загруженного файла;
- «Сгенерировать тексты» — тексты для метрик без текстов;
- «Проверить всё» — полная проверка без нового файла.

Нажмите **Create**. Через минуту-две агент ответит комментарием в этой же задаче.

**3. Где отвечать агенту.**
- Пока нет PR — отвечайте комментарием в задаче. **Каждый ответ начинайте с `@claude`**, иначе агент его не увидит.
- Когда агент сделает первые изменения, он даст ссылку на создание PR. Откройте её и нажмите **Create pull request** (можно выбрать **Create draft pull request**).
- **С этого момента отвечайте только в PR**, тоже начиная с `@claude`. Если ответите в задаче, агент попросит перенести ответ в PR.

**4. Как понять, что проверки зелёные.** Внизу страницы PR — блок проверок: зелёная галочка «All checks have passed» — всё хорошо. Красный крестик — нажмите **Details** рядом с проверкой, чтобы увидеть ошибку, и перешлите её агенту комментарием `@claude`.

**5. Как принять PR.** Если PR черновой — нажмите **Ready for review**. Когда проверки зелёные — **Merge pull request → Confirm merge**.

**6. Где скачать реестр.** Вкладка **Code** → `data/out/registry.csv` → кнопка **Download raw file** (стрелка вниз справа над таблицей). Реестр отдельного стандарта — в `data/out/<std_id>/registry.csv`.

**7. Как поставить «утвержден».** У метрики уже должны быть тексты (задача «Сгенерировать тексты»).
1. Откройте `data/curated/<id>.yaml` (id метрики — колонка `id` в реестре, например `fnmr.yaml`).
2. Нажмите карандаш **Edit this file** и добавьте строку `Статус: утвержден`.
3. **Commit changes…** → выберите **Create a new branch for this commit and start a pull request** → **Propose changes** → **Create pull request**.

## Google Таблица

Ссылка: **[ссылка на таблицу — вставить]**

Таблица — копия общего реестра для чтения. Источник правды — репозиторий.

**Листы:**
- **«Реестр»** — все строки общего реестра (`data/out/registry.json`, вместе с текстами и статусами из `data/curated/`): колонки реестра, затем «Ключ», «Источники», «Синонимы (все)», «Флаги».
- **«Метрики»** — только строки с типом «метрика», те же колонки.
- **«Сводка»** — время обновления (UTC), коммит со ссылкой, подключённые стандарты, число строк и метрик, строки по статусам, флаги по видам.

**Когда обновляется.** Сама — после каждого изменения в `main`, если сборка и проверки прошли. На PR таблица не меняется. Каждый раз листы очищаются и записываются целиком; другие листы таблицы не трогаются.

**Почему её нельзя править.** Любая правка пропадёт при следующей публикации. Листы защищены в режиме предупреждения: таблица спросит, точно ли вы хотите редактировать.

**Как поменять статус или текст.** Через `data/curated/<id>.yaml` в репозитории — раздел «Работа через GitHub», пункт 7. После принятия PR таблица обновится сама.

**Как переопубликовать вручную.** Вкладка **Actions** → слева **CI** → **Run workflow** → ветка `main` → **Run workflow**. Сборка, проверки и публикация пройдут заново.

**Если публикация упала.** Откройте запуск во вкладке **Actions** → задача **publish** → шаг «Publish registry to Google Sheet». Частые причины:
- «ошибка ключа сервисного аккаунта» — в секрет `GOOGLE_SERVICE_ACCOUNT_JSON` вставлен не весь JSON-файл ключа;
- «ошибка Google Sheets API 403» — таблице не дан доступ «Редактор» для email сервисного аккаунта или не включён Google Sheets API;
- «ошибка Google Sheets API 404» — неверный `REGISTRY_SHEET_ID`;
- «публикация пропущена: нет секретов» — секреты не добавлены; это не ошибка, реестр в репозитории в порядке.

Реестр в репозитории от ошибок публикации не зависит.
