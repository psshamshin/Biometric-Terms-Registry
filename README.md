# Реестр терминов и метрик по биометрии из ГОСТов

## 1. Что делает инструмент

Читает PDF ГОСТов по биометрии и собирает реестр терминов и метрик (FMR, FNMR, FAR…). На выходе — реестр каждого стандарта
и общий реестр: одна метрика — одна строка, формулировка каждого стандарта — в своей колонке, дословно.
Тексты для людей (определения, формула) и статус «утвержден» добавляются отдельно, через `data/curated/`.
Реестр публикуется в Google Таблицу для чтения. Источник правды — этот репозиторий.

## 2. Как устроен конвейер

`python run.py` делает всё по порядку:

1. **Разбор стандарта** — текст PDF очищается (колонтитулы, переносы), режется на статьи, из статьи берутся наименования, аббревиатуры, синонимы, определение, примечания.
2. **Тип и область** — метрика или термин по признакам из схемы; область — по разделу стандарта.
3. **Реестр стандарта** — `data/out/<std_id>/` и `report.md`.
4. **Объединение** — записи с одинаковым ключом («Аббревиатура en | Область») из всех стандартов сливаются в одну строку → `data/out/registry.*`, `merge_report.md`.
5. **Слой curated** — поверх общего реестра подмешиваются тексты и статусы из `data/curated/<id>.yaml`.
6. **README** — таблицы разделов 3, 6, 9 пересобираются из конфигов.

После слияния PR в `main` CI повторяет прогон и проверки и публикует реестр в Google Таблицу.

## 4. Как запустить

```bash
python3.12 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python run.py                         # всё
.venv/bin/python run.py config/<std_id>.yaml    # один стандарт
.venv/bin/python -m pytest -q                   # проверки
```

## 5. Как подключить новый стандарт

Загрузить PDF в `data/raw/` и открыть задачу «Добавить ГОСТ» (см. «Работа через GitHub»). Агент работает по `prompts/add_gost.md`:
сначала задаёт вопросы (колонка, url, области, исправления распознавания), потом делает конфиг, эталон и разбор.

## 7. Ключ и id

- **Ключ** — по нему сливаются записи: `FNMR | биометрия · верификация`; без аббревиатуры — `Наименование en | Область`.
- **id** — короткое имя строки (`fnmr`, `biometric-template`), им же называется файл `data/curated/<id>.yaml`.

## 8. Статусы и типы

- **метрика** — оба признака: аббревиатура вида «…R» (или наименование на «rate») и определение со слов «Доля», «Вероятность», «Частота», «Коэффициент». Иначе — **термин**.
- **черновик** — метрика от парсера; **отложено** — термин; **утвержден** и **устарел** — ставит только человек через `data/curated/`.

## 10. Проверки

Запускаются `python -m pytest -q` и в CI на каждый PR. Красная проверка блокирует слияние.

| Проверка | Как работает |
|---|---|
| Схема | каждое значение проходит ограничение своей колонки из `config/registry_schema.yaml` |
| Справочники | тип, статус, область — только из справочников; «утвержден» — только из `data/curated/` |
| Эталоны | по 3–6 статей каждого стандарта, переписанных вручную по сканам страниц, совпадают с разбором посимвольно |
| Регрессия | выход каждого стандарта побайтно совпадает с базовой копией в `data/out/_baseline/` — любая правка кода, меняющая старые результаты, видна сразу |
| Целостность и нумерация | в определении нет обрывков, колонтитулов и чужих номеров; номера статей без пропусков |
| Связи | парная метрика существует в реестре |
| Повторный запуск | два прогона дают побайтно одинаковые файлы |
| Актуальность | CI пересобирает реестр и падает, если закоммиченный `data/out/` или таблицы README устарели |
| Curated | тексты из `data/curated/` проходят схему; изменились формулировки источников — флаг `llm_stale` |
| Формула | цепочка `FNMR = FN / (FN + TP) = FNR = 1 − TPR`: термины — только доли матрицы ошибок и метрики той же области; проверка подставляет числа и требует, чтобы все звенья были равны |
| Публикация | запросы к Google Таблице строятся и проверяются без сети: значения — только текст, формул нет |

## 11. Отчёты

- `data/out/<std_id>/report.md` — по стандарту: флаги, нарушения, эталон, таблица метрик.
- `data/out/merge_report.md` — объединение: какие строки слились, конфликты, слой curated.
- `data/out/<std_id>/abbreviations.csv` — раздел «Сокращения» стандарта.

## 12. Папки и файлы

```
config/       схема реестра, конфиг каждого стандарта, merge.yaml (подключённые стандарты, priority)
src/          конвейер, слой curated, публикация в таблицу
tests/        проверки и эталоны
prompts/      задания для агента: add_gost.md, generate_fields.md
data/raw/     PDF        data/out/     результаты и базовые копии        data/curated/  тексты и статусы
```

## 13. Принятые решения

- Формулировки — дословно; ошибки распознавания правятся только по таблице в конфиге стандарта с основанием по скану.
- Повторы и пересечения стандартов сливаются только на объединении; одинаковый ключ — одна строка.
- Колонки источников — только у подключённых стандартов, в порядке `merge.yaml`.
- Пары метрик: non-, accept/reject, negative/positive; признаки метрики расширяются только по согласованию.
- «утвержден» ставит только человек; `registry.sqlite` не хранится в git и сверяется с `registry.json`.

## Работа через GitHub

1. **PDF** — `data/raw` → **Add file → Upload files → Commit changes**.
2. **Задача** — **Issues → New issue** → шаблон «Добавить ГОСТ», «Сгенерировать тексты» или «Проверить всё».
3. **Ответы агенту** — комментарием, начиная с `@claude`. Сначала в задаче; когда агент даст ссылку на PR — откройте PR и дальше отвечайте только там.
4. **Проверки** — внизу PR: зелёная галочка — можно принимать; красный крестик — **Details** и переслать ошибку агенту.
5. **Принять** — **Merge pull request → Confirm merge**.
6. **Скачать реестр** — `data/out/registry.csv` → **Download raw file**.
7. **«утвержден»** — открыть `data/curated/<id>.yaml` → карандаш → добавить `Статус: утвержден` → **Create a new branch… → Propose changes → Create pull request** → принять после зелёных проверок.
