# Реестр биометрических метрик из ГОСТов

Реестр терминов и метрик биометрии (FMR, FNMR, FAR, FRR и др.), сформированный на основе национальных стандартов.
Для каждой метрики приводятся дословные формулировки всех стандартов, в которых она определена, пояснение для неспециалиста и формула расчёта.

Актуальная версия реестра опубликована в [Google Таблице](https://docs.google.com/spreadsheets/d/1FJ7YqoUL4OeHF_aONszUVQFVKlGMuOboZQGGx2sjFwk/edit?gid=1#gid=1) (только для чтения).
Источником данных является данный репозиторий; таблица обновляется автоматически.

## Принцип работы

Формулировки стандартов извлекает детерминированная программа. Агент (языковая модель) не пишет и не меняет текст стандартов:
он подключает новые документы под контролем владельца реестра и готовит пояснения в отдельном слое данных (`data/curated/`).

**Подключение стандарта** (задача «Добавить ГОСТ»):

1. Агент делает разведку PDF: текст, изображения страниц сканов, ошибки распознавания; строит черновик конфига (`python -m src.new_standard`).
2. Если нужно решение владельца (схема, замена подключённого стандарта, неоднозначный скан, решение вне правил и прецедентов), агент задаёт все вопросы одним комментарием и останавливается. Остальное решает сам и записывает в сводку и в `docs/DECISIONS.md`.
3. Агент создаёт конфиг стандарта и таблицу исправлений распознавания; каждое исправление — с основанием по скану.
4. Агент переписывает 3–6 статей по изображениям страниц — это эталон; он создаётся до первого прогона разбора.
5. Программа разбирает стандарт и проверяет его: схема, эталон, нумерация, целостность, сверка с алфавитным указателем.
6. Стандарт объединяется с общим реестром; результат ранее подключённых стандартов сверяется с утверждёнными копиями (регрессия).
7. Агент запускает `python run.py` и `python -m pytest -q`, коммитит результат в ветку и публикует сводку.

**Тексты** (задача «Сгенерировать тексты»): агент заполняет короткое и длинное определения и формулу метрик в `data/curated/<id>.yaml`
(термины — только по явной просьбе). Связи между записями строятся автоматически. Тексты проверяет `src/validation.py`;
ручная часть проверки — `data/review/validation_review.yaml`, отчёт — `data/out/validation_report.md`.

**Приёмка:** CI повторяет полный прогон и тесты и проверяет, что результат закоммичен. Владелец принимает pull request;
после слияния в `main` реестр публикуется в Google Таблицу. Статус «утвержден» ставит только человек.

## Контроль достоверности

| Гарантия | Способ проверки |
|---|---|
| Формулировки соответствуют PDF | Разбор выполняет программа; склейки переносов и исправления распознавания пишутся в журнал очистки |
| Исправления распознавания обоснованы | Каждое — в конфиге стандарта с основанием по скану; перечень утверждает владелец |
| Разбор корректен | **Эталон:** статьи переписаны по изображениям страниц и сверяются с разбором посимвольно |
| Подключённые стандарты не затронуты | **Регрессия:** результат побайтно сравнивается с утверждённой копией (`data/out/_baseline/`) |
| Данные соответствуют структуре | **Схема:** значения проверяются по ограничениям колонок и справочникам |
| Статьи полные и не смешаны | Нумерация без пропусков, нет обрывов и чужих номеров, сверка с алфавитным указателем |
| Объединение прозрачно | Объединяются записи с одинаковой аббревиатурой и областью; расхождения — флаги и отчёт |
| Пояснения соответствуют источникам | Хранятся отдельно с отпечатком источников (при их изменении — `llm_stale`); формулы и примеры проверяются подстановкой |
| Утверждает человек | Программа ставит только «черновик» и «отложено» |
| Результат воспроизводим | Повторный прогон даёт побайтно те же файлы |
| Публикуются проверенные данные | Только через pull request и после успешного CI |

Сведения, которых нет в документе, не заполняются: в поле «—» и флаг.

## Принятые решения

Полный журнал — `docs/DECISIONS.md`. Коротко о том, что влияет на дословность и связи:

- Знаки сносок (`*`, `<*>`) и тексты сносок внизу страницы в формулировки не входят: убираются как служебный текст и пишутся в журнал очистки.
- Краткие формы («график ХСС», «CMC plot») — синонимы, а не аббревиатуры; аббревиатуры не выдумываются.
- Тире и дефис — как на скане стандарта; исправляются только ошибки распознавания через таблицу `corrections`.
- Пары метрик: `non-`, accept/reject, negative/positive, attack presentation/bona fide presentation.
- Связь «используется в определении» строится по словам из формулировки: словоформы, сокращения, синонимы; по корню головного слова — нет.

## Порядок работы

Все операции выполняются в веб-интерфейсе GitHub.

| Задача | Действия |
|---|---|
| Подключить стандарт | Загрузить PDF в `data/raw` (**Add file → Upload files**); создать задачу по шаблону «Добавить ГОСТ» и указать имя файла |
| Подготовить пояснения | Создать задачу по шаблону «Сгенерировать тексты» |
| Проверить реестр | Создать задачу по шаблону «Проверить всё» |
| Ответить агенту | Комментарий с `@claude`: в задаче до появления pull request, далее — только в pull request |
| Принять изменения | В pull request дождаться успешных проверок и выполнить **Merge pull request** |
| Утвердить метрику | Добавить строку `Статус: утвержден` в `data/curated/<id>.yaml` (**Edit this file → Propose changes**) и принять pull request |
| Получить реестр | `data/out/registry.csv` → **Download raw file**; повторная публикация таблицы — **Actions → CI → Run workflow** |

## Для разработчиков

```bash
python3.12 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python run.py          # полный прогон: стандарты, объединение, пояснения, отчёт проверки, README
.venv/bin/python -m pytest -q    # все проверки
```

- **Правила:** [`docs/RULES.md`](docs/RULES.md) — инструменты и согласованные решения; [`docs/DECISIONS.md`](docs/DECISIONS.md) — журнал решений. Задания агенту — `prompts/add_gost.md`, `prompts/generate_fields.md`, `prompts/validate_fields.md`.
- **Структура реестра:** `config/registry_schema.yaml`; настройки стандарта — `config/<std_id>.yaml`; перечень стандартов — `config/merge.yaml`.
- **Выход:** `data/out/<std_id>/` (стандарт, `report.md`), `data/out/registry.*` и `merge_report.md` (объединение), `data/out/validation_report.md` (проверка текстов), `data/out/_baseline/` (утверждённые копии).
