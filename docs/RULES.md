# Правила и соглашения проекта

Обязательны при любом действии вместе с `prompts/add_gost.md`, `prompts/generate_fields.md` и `prompts/validate_fields.md`.
Здесь — то, что согласовано с владельцем реестра (Павлом) и не написано в промптах.
Структура реестра и ограничения — только в `config/registry_schema.yaml`; при расхождении верна схема.
Если правило здесь расходится с промптом или задачей — не выбирай сам: задай вопрос.
Что решать самому и когда останавливаться — раздел «Что решать самому и когда останавливаться» в `prompts/add_gost.md`.
Файлы с правилами (`docs/RULES.md`, `prompts/add_gost.md`, `CLAUDE.md`) держать согласованными: правило меняется во всех трёх одним коммитом.
Журнал принятых решений — `docs/DECISIONS.md`: перед подключением нового стандарта прочитай его и действуй по прецедентам,
новые решения (область, спорный разбор, исправления, ограничения схемы) дописывай туда же.

## 1. Инструменты

Агент в GitHub может запускать только эти команды. Произвольный Python недоступен:
если нужная проверка ими не покрывается — остановись и спроси, не пиши «проверено».

| Команда | Что делает |
|---|---|
| `python run.py` | все стандарты, объединение, слой curated, генерируемые разделы README |
| `python run.py config/<std_id>.yaml` | один стандарт → `data/out/<std_id>/` |
| `python -m pytest -q` | все проверки (схема, эталоны, регрессия, повторный запуск, README) |
| `python -m src.new_standard data/raw/NNNNN.pdf` | черновик `config/<std_id>.yaml` для нового стандарта и сводка: обозначение, ISO/IEC, «взамен», страницы разделов, нумерация, нужные ключи, статьи с `header_unparsed`; существующий конфиг не перезаписывает (`--out` — другой путь) |
| `python -m src.recon text <pdf>` | текст по страницам в `data/interim/_recon_<файл>/pages/` + тип страниц (скан/текст) |
| `python -m src.recon scan <pdf> <стр> [..]` | полосы скана страницы в PNG (`…/crops/pNN_MM.png`) — открыть и читать глазами |
| `python -m src.recon mixed <pdf> <стр>-<стр>` | подозрения на ошибки распознавания: смесь алфавитов, слова из букв-двойников |
| `python -m src.baseline compare [--std ID] [--ignore-column "колонка"]` | сверка с базовыми копиями: побайтно или «всё, кроме колонки» |
| `python -m src.baseline update [--std ID]` | обновить базовую копию из `data/out/<std_id>/` (после `python run.py`) |
| `python -m src.curated template\|fingerprint\|peers <id>` | заготовка curated-файла, отпечаток источников, что можно использовать в цепочке формулы |
| `python -m src.curated context <id>` | пакет записи для генерации и проверки текстов: формулировки источников, расшифровки аббревиатур (наименования записей, чьи аббревиатуры ru/en стоят в этих формулировках), «Примечания» и «Примеры» статьи, формулировки связанных записей; у метрики ещё справочник формул и формулы связанных метрик (код — `src/context.py`; вызывать через `src.curated`) |
| `python -m src.curated pending [std_id]` | список записей обоих типов, которым нужны тексты: пустые колонки 13 или 14, у метрики пустая 16 без `formula_na`, флаг `llm_stale` (код — `src/pending.py`; вызывать через `src.curated`) |

## 2. Разведка PDF (шаг 0)

1. `python -m src.recon text <pdf>` — найти разделы, колонтитулы, формат статьи по текстовому слою.
2. **Текстовому слою скана не доверять.** Всё, что идёт в реестр (заголовки, определения статей-кандидатов,
   статьи для эталона), сверять с изображением: `python -m src.recon scan <pdf> <стр>` и открыть PNG.
3. `python -m src.recon mixed …` — кандидаты в ошибки. Кириллические «Т», «Р», «А» и латинские T, P, A на скане
   неотличимы: решай по смыслу (переменные N, R, T, k — латиница, как в английской части) и пиши основание.
4. Ошибки вне статей (разделы «Сокращения» и т. п.) не исправляются — только `known_ocr_errors` в конфиге и отчёт.

## 3. Конфиг стандарта `config/<std_id>.yaml`

`std_id` — имя файла без `.yaml` (slug обозначения: `gost_r_71414_1_2024`). Новый ключ кода — со значением
по умолчанию, при котором старые стандарты разбираются как раньше. Ключи (образцы — в подключённых конфигах):

| Ключ | Смысл |
|---|---|
| `standard.designation`, `standard.source_column` | **оба равны названию колонки источника** «{обозначение} ({ISO/IEC})» — по нему проверяются «Ссылки для проверки» |
| `standard.url`, `standard.pdf` | url по правилу `data/raw/NNNNN.pdf` → `https://meganorm.ru/Data/{первые 3 цифры}/NNNNN.pdf`; PDF — путь в `data/raw/`, файл не переименовывать |
| `numbering.anchor` / `section` / `any` | номер статьи в начале строки; код раздела из номера; номер в любом месте (проверка склейки) |
| `bounds.terms` | раздел терминов: строка `start` входит, `end` — нет |
| `bounds.index_ru/index_en`, `index.*` | алфавитные указатели (нет — проверка полноты пропускается); `known_gaps` — объяснённые расхождения |
| `bounds.abbreviations` + `abbreviations.entry/expansion_en` | раздел «Сокращения» → `abbreviations.csv`; строка `start` не входит |
| `cleaning.*` | колонтитул — строка на ≥ 50% страниц; номер страницы; служебные строки раздела |
| `markers.header/example/note` | заголовок до первого «): » (или «]: »), начала примеров и примечаний |
| `markers.abbr_ru_sep`, `abbr_en_sep` | разделители аббревиатур; `abbr_en_sep: null` — английская аббревиатура после «; » |
| `markers.short_forms` | после «; » строка по шаблону — аббревиатура, иначе краткая форма → синонимы |
| `markers.qualifier` | кириллическая скобка после английской — уточнение → первая строка «Примечаний» |
| `markers.groups` | пары скобок групп, например `[...]` для английской группы со скобками внутри |
| `markers.parameters` | «ВЛОИ (N, R, T)» — обозначение, не синоним → «Примечания»; основа — аббревиатура, если обычной нет |
| `markers.note_list` | «П р и м е ч а н и я» + пункты «1 …», «2 …» |
| `corrections` | исправления распознавания (раздел 4) |
| `amendments` | правка статьи по «Изменению № …» стандарта (раздел 8); у статьи флаг `amended` |
| `header_overrides.<пункт>.en_variants` | порядок английских вариантов (только перестановка) |
| `areas.sections` / `areas.exceptions` | раздел → Область; исключения — по номеру пункта; значения только из справочника |

Черновик конфига даёт `python -m src.new_standard`: он определяет всё, что выводится из текста PDF. Вручную остаются
`corrections` (по скану), `known_ocr_errors`, `known_gaps`, `header_overrides`, исключения `areas`, эталон.
Область в черновике — «биометрия · общее» для каждого раздела: предложи значение по смыслу и запиши в `docs/DECISIONS.md`.
Генератор проверен тестом на подключённых стандартах: находит те же ключи и тот же шаблон нумерации, что их конфиги.

### Рост правил разбора

- Новый вариант оформления статьи — **новый ключ конфига** (значение по умолчанию сохраняет разбор старых стандартов)
  и **тест на статью-пример**: дословная статья с ожидаемым разбором.
- Поведение существующих ключей не меняется.
- Новому стандарту нужно больше трёх новых ключей — остановись и спроси, с рекомендуемым вариантом.
- В сводку каждого подключения: сколько ключей конфига использовано и сколько добавлено.

**YAML:** номера пунктов и разделов — в кавычках (`'3.10'`, `'37.01'`): без кавычек `3.10` читается как число 3.1.

## 4. Исправления распознавания (`corrections`)

- Запись: `пункт` (в кавычках), `было`, `стало`, `основание` — страница скана и что на ней видно.
- `было` — текст **после** очистки: переносы склеены, двойные пробелы схлопнуты. Должно встретиться в статье ровно один раз.
- Только ошибки, подтверждённые сканом (или неотличимые на скане буквы-двойники — с основанием по смыслу).
  Опечатки самого стандарта не исправляются. Таблицу показать Павлу до прогона.
- Применённые исправления пишутся в журнал очистки, у статьи — флаг `ocr_fixed`.

## 5. Эталон `tests/golden_<std_id>.yaml`

- 3–6 статей: метрики, сложные случаи разбора, статья, которая сольётся с другим стандартом.
- Текст — **с изображения страницы** (`src.recon scan`), не с текстового слоя и не из разбора. Перенос слова склеивать без дефиса.
- Поля, которых нет на изображении (id, Область, Тип, Статус, Ссылки, Связанные термины), выводятся по правилам вручную.
- `~` — поле не заполнено; `"—"` — поле должно быть пустым. В шапке — откуда переписано (страницы, полосы).
- Писать до первого прогона разбора.

## 6. Регистрация стандарта и базовая копия

- В `config/merge.yaml` — только после того, как проверки стандарта прошли:
  `config`, `golden`, `miro: null` (сверки с Miro нет), `connected: <дата>` (нужна для README); в `priority` — в конец списка.
- С этого момента у стандарта есть колонка источника (порядок колонок — как в `merge.yaml`). Колонка новая;
  если стандарт заменяет подключённый — вопрос Павлу (переименовать колонку или добавить новую).
- Отпечаток curated-файла считается только по **заполненным** колонкам источников: новая пустая колонка отпечатки не меняет,
  появившаяся в ней формулировка для существующей метрики — меняет, и сборка ставит `llm_stale`. После подключения
  стандарта отпечатки руками не пересчитывать (пересчёт — только при смене правила расчёта, один раз, без правки текстов).
- Затем `python run.py` → `python -m src.baseline update --std <std_id>` → `python -m pytest -q`.

## 7. Изменения схемы, кода и регрессия

1. Изменение структуры (колонки, справочники, признаки метрики, правила пар и объединения) — только с согласия Павла.
   Ограничения формата полей (`pattern`, длины) ловят ошибки разбора, а не проверяют «красоту». Если значение дословно
   из стандарта, подтверждено сканом, а ограничение его не пропускает — минимально расширь ограничение сам, не останавливайся:
   запиши в историю схемы и в «Решения, принятые самостоятельно». Проверки на смешение алфавитов, пустые значения
   и мусор распознавания не ослаблять. Формат полей: Наименование en — латиница любого регистра, цифры, пробел, дефис;
   Аббревиатура en — латиница, цифры, дефис; Аббревиатура ru — кириллица любого регистра, цифры, дефис; длины — по схеме.
2. После изменения: `python -m src.baseline compare --ignore-column "<изменённая колонка>"`.
   Всё, кроме неё, должно совпасть; в новой или убранной колонке — проверить значения (обычно везде «—»).
3. Только потом `python run.py` и `python -m src.baseline update`. Записать изменение в историю в шапке
   `config/registry_schema.yaml` и в docstring `tests/test_regression.py`.
4. Новый флаг — в `flags` (когда ставится) **и** в `flag_actions` (что делать), иначе падает тест README.
5. Новая библиотека — с точной версией в `requirements.txt`, иначе CI не установит её.
6. Выход (`data/out/`) и README не править руками: `python run.py` и закоммитить результат.

## 8. Согласованные решения

- Сбор — без слияний; повторы внутри стандарта и пересечения стандартов сливаются только на объединении (одинаковый ключ).
- Колонка источника на несколько пунктов: тексты совпадают — `п. A, B — текст`, иначе `п. A — …; п. B — …`.
- «исключен «…»» — устаревший термин в «Исключённые», статья остаётся.
- Синонимы — без ограничения числа. Краткие формы — синонимы; обозначения с параметрами — нет.
- Области: FAR/FRR — «система целиком» (транзакции), FMR/FNMR — «верификация» (сравнения), FNIR/FPIR/TPIR — «идентификация».
- Пары метрик: non-, accept/reject, negative/positive, attack presentation/bona fide presentation (`pairs` в схеме). Без пары — «—» и `no_pair`; текст причины `no_pair` не менять (он в базовых копиях).
- Признаки метрики не расширять без согласования (SEL, pre-selection error, penetration rate — термины).
- Формула — цепочка равенств в пределах области (`prompts/generate_fields.md`, раздел `formula` схемы); без формулы — `formula_na`.
- «утвержден» и «устарел» ставит только человек через `data/curated/`.
- Тексты метрик (колонки 13, 14, 16) и терминов (13, 14) — по `prompts/generate_fields.md`. Направление «лучше» не указывается нигде: ни «Ниже/Выше — лучше»,
  ни «Чем ниже / выше значение…». Короткое определение — только смысл, до 10 слов. Объяснять, как значение меняется при настройке
  системы, можно только по «Примечаниям» источников.
- Метрики и термины — два типа записей с одним набором правил; различия только в схеме (`config/registry_schema.yaml`), CI падает при нарушении:
  длинное определение — метрика 300–1000, термин 100–700 символов; короткое — до 10 слов у обоих; формула — у метрики обязательна
  (или `formula_na`), у термина всегда «—» и флага нет; «утвержден» — метрике нужны 13, 14 и 16 (или `formula_na`), термину 13 и 14.
- Статус от парсера — только «черновик» у обоих типов. «Отложено» остаётся в справочнике, но парсер его не ставит.
  «утвержден» и «устарел» — только из `data/curated/`.
- Тексты записи пишутся только по её пакету (`python -m src.curated context <id>`); сгенерированные тексты других записей в пакет не входят,
  опора в `prompts/validate_fields.md` проверяется только по пакету. Формулы — только у метрик: справочник `formula` схемы или цепочка из формул
  связанных метрик; новая формула сначала получает тест подстановки условных чисел, потом попадает в справочник; иначе `formula_na`.
- Список записей для генерации — только `python -m src.curated pending`, не по памяти.
- Связи: «парная метрика» (`pairs`), «дополнение» (`complements`, FNIR ↔ TPIR: сумма равна 1, 71414.1 п. 3.25 «Примечания»)
  и «используется в определении» — строится автоматически: запись, чьё наименование или синоним названы в формулировке источника
  (по стандарту — при сборке, в общем реестре — по объединённым формулировкам); `src/links.py`.
- Проверка текстов — `prompts/validate_fields.md`; отчёт `data/out/validation_report.md` строит `python run.py`,
  ручная часть — `data/review/validation_review.yaml` (привязана к хэшу текстов и источников).
- Аббревиатуры в текстах: в длинном определении при первом упоминании расшифровываются по пакету («Наименование (ABBR)» / «ABBR (наименование)»);
  в коротком — по возможности без аббревиатур. Собственная аббревиатура записи и ГОСТ/ИСО/МЭК/ISO/IEC не считаются. Проверка — блок «е»
  (`src/validation.py`; `pending` её не показывает).
- Записи реестра, названные в формулировках источников, но не указанные в «Связанных терминах», проверка выписывает (блок «д»).
- «Изменение № …» стандарта, приложенное к PDF после основного текста, само не применяется: правку статьи — только по согласованию.
  Согласованная правка — ключ конфига `amendments` (`пункт`, `изменение`, `было`, `стало`, `основание`; `было` — ровно один раз в строке
  статьи, текст по скану); у статьи флаг `amended`, формат колонки источника не меняется, «Примечания» — как были, если изменение их не трогает.
- Перенос дефисом: по тексту стандарта; иначе латиница — дефис, кириллица — склейка, флаг `hyphen_guess`.
- `registry.sqlite` не в git и не в базовых копиях: байты зависят от версии SQLite; содержимое сверяется с `registry.json`.
- Python 3.12; версии — в `requirements.txt`.
- Сверки с Miro нет (у 2382-37 сверка осталась из первой версии и входит в регрессию).

## 9. Ветки

- Агент в GitHub: ветку создаёт action (`claude/issue-…`); первые коммиты → ссылка на PR → дальше только в PR.
- Локальная работа: долгоживущая ветка `dev` (несколько независимых фич — несколько `dev-<тема>`), PR `dev` → `main`.
  Ветку на каждое изменение не создавать.

## 10. Конфиденциальность

- Формулировки стандартов дословные — внутренние данные. Наружу (публичные ссылки, внешние сервисы) не публиковать.
- Google Таблица открыта только конкретным людям и сервисному аккаунту, без доступа «по ссылке».
- Ключи — только в секретах GitHub; не печатать, не писать в файлы и логи.
