# Проверка сгенерированных текстов

> **Перед выполнением прочитай `docs/RULES.md` и `prompts/generate_fields.md`**: правила текстов — там. Здесь только порядок проверки.

## Задача

Проверить колонки 13, 14, 16 у каждой записи, где есть хотя бы один текст (метрики и термины), и записать результат
в `data/out/validation_report.md`. Проверка повторяема: те же тексты и источники дают тот же отчёт.
Статус «утвержден» не ставь, тексты, не вошедшие в замечания, не трогай.

## Источники записи — только пакет

Опору проверяй **только по пакету записи**: `python -m src.curated context <id>`.
Всё, чего в пакете нет, — утверждение без опоры (блок а). Тексты других записей в пакет не входят и опорой не служат.

0. В любом пакете: `расшифровки_аббревиатур` — наименования записей, чьи аббревиатуры стоят в формулировках источников и в «Примечаниях» и «Примерах» статьи.
1. Метрика: формулировки источников; «Примечания» и «Примеры» статьи; формулировки записей из «Связанных терминов»; справочник формул схемы и формулы связанных метрик.
2. Термин: формулировки источников; «Примечания» и «Примеры» статьи; формулировки записей «используется в определении». Формул в пакете нет.
3. Запись, названная в тексте, но отсутствующая в пакете, — замечание.

## Блоки

| Блок | Что проверяется | Кто |
|---|---|---|
| ф. Формат | Длинное: метрика 300–1000, термин 100–700 символов (из схемы); короткое ≤ 10 слов; в длинном нет счётчиков TP/FP/TN/FN и фраз о формуле; у метрики пример помечен «условный»; у термина — пример из частного случая определения (числа в тексте сверь с пакетом в блоке а); статус «черновик» | `src/validation.py` |
| а | Каждое утверждение длинного и короткого определений опирается на источники записи. Утверждения без опоры выпиши: зависимости от настройки системы, оценки, причины, которых нет в источниках; ссылки на другие записи, сказанное о которых не подтверждается их формулировкой | агент |
| б | Короткое не противоречит длинному и источникам; не сужает («живой человек» вместо «подлинное предъявление») и не расширяет смысл; пример считается по тому, что считает определение (транзакции, сравнения, предъявления) | агент |
| в | Формулы проверяются **только у метрик**. **Метрика:** прямая формула — по справочнику (`formula.direct` схемы); цепочка — по схеме; условные числа из примера, подставленные в формулу, дают процент из примера (TP/FP/TN/FN назначь по соглашению реестра); при `formula_na` проверь пример. **Термин:** формула «—», флага `formula_na` нет | `src/validation.py` + агент |
| г | Направления «лучше» нет ни у метрики, ни у термина: в коротком и длинном определениях нет «Ниже/Выше — лучше» и «Чем ниже / выше значение…» | `src/validation.py` |
| е | Аббревиатуры: в длинном определении при первом упоминании расшифрованы («Наименование (ABBR)» или «ABBR (наименование)»); расшифровка совпадает с наименованием из пакета (`расшифровки_аббревиатур`, `наименование` связанной записи) — сверяет агент; в коротком определении аббревиатур по возможности нет. Собственная аббревиатура записи и ГОСТ/ИСО/МЭК/ISO/IEC не считаются | `src/validation.py` (наличие расшифровки) + агент (соответствие пакету) |
| д | Записи реестра, названные в формулировках источников этой записи, но не указанные в «Связанных терминах». Связь «используется в определении» строится автоматически (`src/links.py`); блок выписывает пропуски (например, имя в другом падеже) | `src/validation.py` |

## Порядок

1. `python run.py` — отчёт со строками «ревью нет (хэш …)» у записей без ручной проверки.
2. Для каждой такой записи проверь блоки а, б и подстановку чисел в блоке в. Запиши в `data/review/validation_review.yaml`:
   `id: {hash: <хэш из отчёта>, a: [...], b: [...], c: [...]}`; пустой список — замечаний нет, иначе — одна строка на замечание:
   «что сказано — почему нет опоры».
3. Исправь замечания, найденные в п. 2 и в отчёте, — в `data/curated/<id>.yaml` (по правилам `prompts/generate_fields.md`).
   Колонки источников, наименования и статусы не трогай. Блок д не правь: перечисли в сводке.
4. `python run.py` — хэш изменённых записей изменился: снова п. 2 для них, пока в отчёте нет замечаний кроме блока д.
5. Добавь в `history` файла `validation_review.yaml` строки «до / после» по блокам (проценты из отчёта).
6. `python -m pytest -q`.

## Отчёт

`data/out/validation_report.md` строится при каждом `python run.py`: охват, доля записей без замечаний по блокам (метрики и термины
отдельно), список правок, таблица по записям, история. Руками не править — только через `python run.py` и
`data/review/validation_review.yaml`.

## В сводку

- проценты по блокам до и после;
- список исправленных замечаний (запись — что было — что стало);
- блок д: записи, которые остались без связи;
- записи, которые человеку стоит проверить в первую очередь (`formula_na`, `llm_failed`, расхождения между источниками).
