# Подключение нового ГОСТа и проверка всего реестра

> **Перед выполнением прочитай `docs/RULES.md` и опирайся на него**: там согласованные решения, инструменты и правила, которых нет в этом промпте. При расхождении — спроси.

## Что это за инструмент

Парсер собирает реестр терминов и метрик по биометрии из ГОСТов. Инструмент автономный: ни с чем внешним не синхронизируется, Miro и другие доски не используются.

Как он устроен:

- **Общее для всех стандартов** лежит в `config/registry_schema.yaml`: колонки реестра, справочники, ограничения, правила пар метрик, флаги.
- **У каждого стандарта свой конфиг** `config/{std_id}.yaml`: всё, что зависит от этого стандарта.
- **Список подключённых стандартов** и порядок `priority` лежат в `config/merge.yaml`.
- **Выход:**
  - по каждому стандарту — `data/out/{std_id}/`;
  - общий реестр — `data/out/registry.*` и `data/out/merge_report.md`;
  - базовые копии для регрессии — `data/out/_baseline/{std_id}/`.

**Когда использовать этот промпт:**

- в `data/raw/` появился новый PDF — выполни все шаги;
- нового PDF нет, нужна только проверка — выполни шаги 6, 8 и 9.

## Главные правила

1. **Сначала сбор, потом сопоставление.** На сборе из каждого стандарта берётся всё как есть, ничего не убирается и не сливается. Повторы и пересечения, в том числе внутри одного стандарта, обрабатываются только на шаге объединения.
2. **Ничего не ломать.**
   - Выход каждого подключённого стандарта до и после твоих изменений побайтно совпадает с его базовой копией.
   - Эталонные тесты всех стандартов проходят.
   - Если согласованное изменение схемы меняет выход старых стандартов, сверяй всё, кроме изменённого места. Проверь само изменение и только потом обнови базовые копии.
3. **Колонки источников — только у подключённых стандартов.**
   - Колонка источника есть, только если стандарт есть в `merge.yaml`.
   - Колонок «на будущее» нет: список колонок источников строится из `merge.yaml`, вручную в схеме его не держат.
   - Порядок колонок источников — как в `merge.yaml`.
   - Сейчас в схеме есть колонка «ГОСТ Р 58624.3-2019 (ИСО/МЭК 30107-3)», а сам стандарт не подключён. Её нужно убрать до шага 0. Регрессия: убедись, что она была пустой («—») во всех строках, сверь остальное с базовыми копиями и обнови их.
4. **Структуру реестра не меняй без моего согласия:** колонки, кроме колонок источников по правилу 3, значения справочников, признаки метрики, правила пар и объединения.
   Ограничения формата полей (`pattern`, длины) — не структура: если дословное значение из стандарта, подтверждённое сканом, не проходит ограничение, минимально расширь его сам (история схемы, «Решения, принятые самостоятельно»). Проверки смешения алфавитов, пустых значений и мусора распознавания не ослабляй.
5. **Конфиги подключённых стандартов не трогай.** Исключение — ошибка в конфиге, и тогда только с моего согласия.
6. **Текст стандарта — дословно.** Исправления распознавания — только по таблице в конфиге, с основанием по скану и записью в журнал очистки.
7. **Разбор, специфичный для одного стандарта** (`if std_id == ...`), в коде запрещён. Всё специфичное — в конфиг. У нового ключа конфига значение по умолчанию сохраняет поведение старых стандартов.
8. **LLM не используется.** Колонки «Переработанное длинное определение», «Короткое определение» и «Формула *» заполняются «—».
   Тексты метрик и терминов пишет только `prompts/generate_fields.md` в слое `data/curated/`.
9. **Не выдумывай данные.** Если поле не извлекается — «—» и флаг.
10. **Падает проверка — чини разбор, а не проверку.** Ослабить проверку можно только с моего согласия; исключение — ограничение формата поля по правилу 4.

## Что решать самому и когда останавливаться

**Решай сам, без вопросов.** Каждое такое решение записывай в сводку (шаг 9), в раздел «Решения, принятые самостоятельно»:

- **url:** `data/raw/NNNNN.pdf` → `https://meganorm.ru/Data/{первые 3 цифры}/NNNNN.pdf`.
- **Колонка источника:** новая, «{обозначение} ({ISO/IEC})». `priority` — в конец списка.
- **Отпечатки curated-файлов:** считаются только по заполненным колонкам источников. Новая пустая колонка их не меняет;
  если в новом стандарте есть формулировка для существующей метрики, сборка ставит `llm_stale` — это ожидаемо, отпечатки руками не правь.
- **Область:** значение справочника по смыслу раздела; исключения — по пунктам.
- **Аббревиатуры ru и en:** из текста стандарта — заголовки, определения, «Сокращения». Не нашлись — «—».
- **Служебный текст:** ссылки на библиографию (`[1], [2]`), сноски, колонтитулы, водяные знаки — убирать и писать в журнал очистки.
- **Ошибки распознавания,** которые подтверждает скан, — исправлять по таблице в конфиге.
- **Эталон** — по сканам.
- **Изменения кода,** после которых регрессия всех стандартов зелёная, — делать без остановки и описывать в сводке.
- **Всё остальное** — по аналогии с подключёнными стандартами и журналом `docs/DECISIONS.md`.
  Прочитай журнал до шага 0; каждое новое решение (область, спорный разбор, исправления) допиши туда же.

**Останавливайся и спрашивай, только если:**

- нужно изменить схему: колонки, справочники, признаки метрики, правила пар или объединения (ограничения формата полей — по правилу 4, сам);
- новый стандарт заменяет уже подключённый;
- меняется выход уже подключённых стандартов;
- скан нельзя прочитать однозначно;
- решение не выводится ни из правил, ни из прецедентов;
- новому стандарту нужно **больше трёх новых ключей конфига** (шаг 2) или изменение поведения существующего ключа.

Если таких вопросов нет, после разведки не останавливайся — доводи работу до сводки.
Каждый вопрос задавай вместе со своим рекомендуемым вариантом.

## Шаг 0. Разведка — до любого кода

0. **Черновик конфига:** `python -m src.new_standard data/raw/NNNNN.pdf` — обозначение, ISO/IEC, «взамен», страницы разделов,
   нумерация, колонка, url, место в `priority`, нужные ключи конфига, статьи с `header_unparsed`. Результат — исходная точка
   для пунктов ниже; скан и вручную остаются `corrections`, `known_ocr_errors`, `known_gaps`, `header_overrides`, исключения областей.
1. **Новый файл.** Это PDF в `data/raw/`, на который не ссылается ни один конфиг. Найди:
   - обозначение, название, год;
   - соответствие ISO/IEC и его вид (IDT, MOD, NEQ);
   - пометку «взамен …».
2. **Тип PDF.** Текстовый или скан. Если скан — опиши качество распознавания и найденные ошибки, сверив их со сканом.
3. **Разделы.** «Термины и определения», «Сокращения», «Обозначения», алфавитные указатели — страницы начала и конца каждого или «нет».
4. **Ссылочные термины** («применены термины по …»). Их не разбираем — только перечисли стандарты.
5. **Устройство статьи:**
   - нумерация и регулярное выражение для неё;
   - формат заголовка: русский термин, аббревиатуры, английская группа, скобки, разделитель перед определением;
   - синонимы, краткие формы, обозначения с параметрами, уточнения в скобках;
   - примеры и примечания, в том числе «Примечания» с пунктами;
   - статьи, которые переходят на следующую страницу.
6. **Служебные строки:** колонтитулы, номера страниц, заголовки подразделов, водяные знаки.
7. **Формулы метрик** — только перечисли пункты и страницы.
8. **Дословные образцы:**
   - 3 статьи подряд;
   - 2 сложные статьи;
   - фрагмент раздела «Сокращения», если он есть.
9. **Кандидаты в метрики** по признакам из схемы — таблица «пункт — термин — А — Б — итог». Отдельно перечисли статьи, похожие на метрику, которые правило не ловит. Правило сам не расширяй.
10. **Пары метрик** по правилам `pairs` из схемы. Какие пары находятся, у каких метрик пары нет, нужна ли новая пара.
11. **Область.** Выбери значение справочника для разделов и исключения по пунктам. Если нужного значения в справочнике нет — спроси (изменение справочника).
12. **Колонка источника.** Название в формате «{обозначение} ({ISO/IEC})», колонка новая. Если стандарт заменяет подключённый — спроси, переименовать его колонку или добавить новую.
13. **url для «Ссылок для проверки».** По правилу `data/raw/NNNNN.pdf` → `https://meganorm.ru/Data/{первые 3 цифры}/NNNNN.pdf`.
14. **Пересечение с общим реестром.** Какие записи совпадут по ключу, какие — по Наименованию en при разной аббревиатуре или области, где разойдётся Наименование ru. Отдельно — повторы внутри самого стандарта.
15. **`priority`** — новый стандарт в конец списка.
16. **Отличия от уже подключённых стандартов** и что придётся обобщить в коде.
17. **Вопросы ко мне** — только по критериям раздела «Что решать самому и когда останавливаться», каждый с рекомендуемым вариантом.

**Остановись и дождись ответов, только если есть вопросы по этим критериям.** Иначе иди к шагу 1.

## Шаг 1. Конфиг нового стандарта

1. Возьми черновик `python -m src.new_standard` как `config/{std_id}.yaml`. `std_id` — slug обозначения, например `gost_r_58624_3_2019`.
   Существующие конфиги генератор не перезаписывает, и ты их не трогаешь (правило 5).
2. Проверь и дополни его по тем же ключам, что у подключённых стандартов:
   - нумерация и границы разделов;
   - маркеры заголовка, примеров и примечаний;
   - служебные строки;
   - колонка, url, область;
   - исправления распознавания, `known_gaps`.
3. Если сканом подтверждаются ошибки распознавания, составь таблицу исправлений: пункт, было, стало, где на скане. Внеси её в конфиг и покажи в сводке.
4. Покажи конфиг в сводке.

## Шаг 2. Обобщение кода — только если конфига не хватает

0. **Граница роста правил.** Новый вариант оформления — новый ключ конфига и тест на статью-пример (дословная статья
   с ожидаемым разбором). Поведение существующих ключей не меняется. Нужно больше трёх новых ключей или изменение
   существующего — **остановись и спроси** с рекомендуемым вариантом. Подсчитай ключи для сводки.
1. Опиши, что не описывается конфигом, какие функции меняются и как сохраняется поведение подключённых стандартов (новый ключ — со значением по умолчанию).
2. Если после изменения регрессия всех стандартов зелёная — делай без остановки и опиши в сводке. Если меняется выход подключённых стандартов или схема — **остановись** и покажи план.
3. После изменений прогони все подключённые стандарты и сверь их выход с базовыми копиями.

## Шаг 3. Эталон нового стандарта

1. `tests/golden_{std_id}.yaml` на 3–6 статей:
   - метрики;
   - сложные случаи разбора;
   - статья, которая сольётся с другим стандартом, если такая есть.
2. Заполняй эталон **по изображениям страниц**, а не по текстовому слою и не по своему разбору. Если что-то читается неоднозначно — оставь поле пустым и отметь.
3. Тест на эталон пиши до прогона разбора.

## Шаг 4. Разбор нового стандарта

1. Конвейер — общий для всех стандартов: извлечение → очистка → разбиение на статьи → разбор полей → тип и статус → область, ключ, id → пары метрик → реестр стандарта.
2. Выход — `data/out/{std_id}/`: `registry.csv`, `registry.json`, `registry.sqlite`, `report.md`, `abbreviations.csv` (если есть «Сокращения»).
3. Проверки стандарта:
   - схема и справочники;
   - нумерация и целостность статьи;
   - полнота по указателю, если указатель есть;
   - дубли ключа — информация, не ошибка;
   - пары;
   - эталон;
   - повторный запуск.
4. Если проверки прошли, добавь стандарт в `merge.yaml`. С этого момента у него есть колонка источника.

## Шаг 5. Объединение

Правила одинаковы для записей из разных стандартов и для записей одного стандарта.

### Какие записи объединяются

| Ситуация | Что делать |
|---|---|
| Ключ «Аббревиатура en \| Область» совпал | Одна строка |
| Аббревиатуры нет, совпали Наименование en и Область | Одна строка |
| Аббревиатура en совпала, Область разная | Не объединять, флаг `area_conflict` |
| Наименование en совпало, аббревиатура или область разные | Не объединять, флаг `merge_candidate` |

Наименование en сравнивается без учёта регистра, дефис считается равным пробелу.

### Как заполняются колонки объединённой строки

| Колонка | Правило |
|---|---|
| Колонки источников | Каждая — из своего стандарта; если записи нет — «—». Несколько записей одного стандарта: тексты совпадают — `п. A, B — текст`, различаются — `п. A — …; п. B — …` |
| Ссылки для проверки | Объединение без повторов |
| Наименование ru, Аббревиатура ru, Наименование en | Из первого по `priority` источника. Другое значение уходит в «Синонимы», флаг `name_conflict` |
| Синонимы | Объединение без повторов, в порядке `priority`; ограничения на число синонимов нет |
| Тип сущности | Одинаковый — он. Разный — «термин», «отложено», флаг `type_conflict` |
| Статус | Метрика — «черновик», термин — «отложено» (термин с текстами из слоя curated — «черновик», его ставит curated-файл) |
| Связанные термины | Объединение связей («парная метрика», «дополнение» — `pairs`, `complements` схемы); каждая связь указывает на существующую запись |
| id | Из первой по `priority` записи |
| LLM-поля, «Есть в NIST», «Забираем в MRR» | «—» |

## Шаг 6. Полный прогон и проверки всех стандартов

1. Прогони все стандарты из `merge.yaml` и объединение одним запуском.
2. Проверки:
   - **каждый стандарт** — проверки шага 4;
   - **общий реестр** — схема, справочники, дубли ключа, связи, конфликты объединения;
   - **регрессия** — выход каждого стандарта совпадает с его базовой копией;
   - **эталоны всех стандартов**;
   - **повторный запуск** — два прогона дают побайтно одинаковые файлы;
   - **README** — список стандартов, флагов и цифры в нём совпадают с фактическими (см. шаг 8).
3. Флагов без пояснения быть не должно: у каждого флага пояснение берётся из схемы.

## Шаг 7. Базовая копия

После того как всё прошло, заведи базовую копию нового стандарта в `data/out/_baseline/{std_id}/`. Если изменения затронули старые стандарты, обнови их копии по правилу 2.

## Шаг 8. README

Обнови `README.md`. Его читают не только разработчики: он объясняет, что это за реестр и почему ему можно доверять.
Стиль — формальный, деловой, без разговорных оборотов; коротко и без пересказа кода. Разделы:

1. **Вступление** — что это за реестр (2–3 предложения) и ссылка на Google Таблицу.
2. **Принцип работы** — схема этапов на Mermaid (`flowchart`): загрузка PDF → разведка → вопросы владельцу → конфигурация и исправления → эталон → разбор → проверки → объединение → пояснения → CI → принятие PR → публикация.
3. **Контроль достоверности** — таблица «гарантия — способ проверки»: дословный разбор скриптом, исправления распознавания с основанием по скану, эталоны по изображениям, регрессия, схема, целостность, честное объединение, слой пояснений модели с отпечатком и проверкой формул, «утвержден» только человеком, повторяемость, CI перед публикацией. Плюс абзац о том, что модель на разведке останавливается с вопросами и ничего не выдумывает.
4. **Подключённые стандарты** — генерируется: стандарт, статей, метрик, эталон по сканам, дата подключения.
5. **Порядок работы** — таблица действий в веб-интерфейсе GitHub: добавить ГОСТ, сгенерировать пояснения, отвечать агенту, принять PR, утвердить метрику, скачать реестр.
6. **Для разработчиков** — запуск, где правила (`docs/RULES.md`), структура, отчёты.
7. **Флаги** — генерируется, в свёрнутом блоке `<details>` мелким шрифтом: это служебная информация.

Схему данных (таблицу колонок) в README не выносить: она в `config/registry_schema.yaml`.
Разделы 4 и 7 генерируются из конфигов и схемы при каждом прогоне — между маркерами `<!-- AUTO:… -->` руками не править.

## Шаг 9. Сводка

Коротко:

- что подключено;
- ключей конфига использовано (из сводки `python -m src.new_standard`) и добавлено новых;
- таблица по стандартам: статей, метрик, нарушений схемы, эталон, регрессия;
- общий реестр: строк, метрик, объединено, конфликты;
- что не прошло и почему;
- раздел «Решения, принятые самостоятельно»: каждое решение из списка «Что решать самому» — что выбрано и почему
  (те же решения дописаны в `docs/DECISIONS.md`);
- вопросы ко мне (каждый с рекомендуемым вариантом).

## Критерии готовности

- Новый стандарт разобран своим конфигом, специфичного кода нет.
- Колонки источников есть только у подключённых стандартов.
